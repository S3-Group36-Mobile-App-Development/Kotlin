# Concurrencia, almacenamiento y conectividad eventual

**Regla para responder:** `suspend` permite suspender una función; **no implica** por sí mismo que corra fuera del hilo principal. En el juego hay trabajo CPU muy pequeño (20 posiciones) que permanece en UI; E/S de token y conciliación usa IO, Room proporciona DAO suspendidos/Flow y los agregados del historial se calculan en Default. No hay `Thread` manual ni trabajo ficticio.

## 1. Cada concepto solicitado, dónde se usa y qué protege

| Concepto | Uso real en Juegos | Por qué está ahí | Si se elimina o cambia sin equivalente |
|---|---|---|---|
| `suspend` | `GameSessionDao` (consultas/escrituras), `GameSessionRepository.currentOwner/save/history/refreshFromBackend`, `GameApiService` POST/GET, `GameSyncProcessor.sync`, `GameHistoryRefresher.refresh`, `GameSyncWorker.doWork`, `GameSyncScheduler.enqueuePending`. | Permite esperar operaciones de Room, WorkManager o Retrofit sin bloquear el llamador por una espera síncrona; **no** decide el dispatcher. | Hacer E/S bloqueante en main puede congelar la UI; habría que rediseñar llamadas asíncronas, no solo quitar una palabra clave. |
| `launch` | `viewModelScope.launch` en `loadHistory`, refresco GET, observación de `running` y espera de guardado; `applicationScope.launch` para revisar pendientes; `AppContainer` y `ZenNavGraph` disparan trabajo de sincronización. | Inicia tareas sin resultado directo para el llamador: observación continua, programación y actualización de estado. | Ejecutar directamente una colecta infinita de `Flow` impediría continuar; usar un scope no ligado a la pantalla podría dejar trabajos vivos tras salir. |
| `async` y `await` | `BubbleGameViewModel.savePending`: `applicationScope.async { repository.save(session); ... enqueue }` y `viewModelScope.launch { write.await() }`. | La escritura puede terminar aunque la pantalla se destruya; mientras existe, el ViewModel espera el **resultado** para mostrar Saved/Failed. `async` aquí no lanza varias escrituras en paralelo artificialmente. | Mover la escritura solo a `viewModelScope` permite cancelarla al salir; marcar Saved antes de `await` afirmaría guardado sin confirmación. Conservar el mismo UUID permite retry seguro. |
| `viewModelScope` | Observa Room, refresca historial remoto, observa estado del worker y espera el resultado de la escritura. | Su vida está asociada al ViewModel de la ruta Juegos. La UI puede irse sin retener observaciones de pantalla. | Un scope global para esos colectores podría mantener GET/observadores y UI obsoleta; hacer trabajo pesado directamente en main causaría jank. |
| `applicationScope` | `ZenMindApplication.applicationScope = CoroutineScope(SupervisorJob() + Dispatchers.IO)`; lo usa el guardado y la programación de pendientes de Juegos, además de disparos al recuperar red/login. | Permite terminar una escritura iniciada incluso si el ViewModel se destruye; `SupervisorJob` evita que una excepción de un hijo cancele automáticamente todos los demás. | Si se liga la escritura solo a una pantalla, salir enseguida puede cancelar el guardado. **No** garantiza completar una escritura si Android mata el proceso antes de que Room la confirme. |
| `Dispatchers.IO` | Scope de aplicación; `withContext(IO)` en `GameSessionRepository.currentOwner/save/history`, `GameHistoryRefresher.refresh` y lectura del token en `GameSyncWorker`. | Lectura de token/cifrado, SQL y conciliación con GET son E/S o tareas relacionadas. El GET Retrofit es suspendido; envolver el proceso de conciliación mantiene validación e inserciones fuera de main. | Una lectura/cifrado o manejo de datos bloqueante en main podría congelar la pantalla. No se debe concluir que toda función `suspend` necesita IO: los DAO suspendidos usan la infraestructura de Room. |
| `Dispatchers.Default` | `withContext(Default) { calculateGameStatistics(history, owner) }` dentro de `BubbleGameViewModel.loadHistory`. | Es agregación en memoria (CPU); mantiene esa operación fuera de main cuando crece el historial. | Calcular sobre un historial grande en main podría producir tirones. No se crearon esperas, loops costosos artificiales ni threads para exhibir multithreading. |
| `withContext` | Repositorio/refrescador/worker para IO; ViewModel para estadísticas en Default. | Cambia **el contexto de ejecución de un bloque** y regresa al llamador al terminar, manteniendo el resultado o la excepción. | Quitar IO de E/S potencialmente bloqueante o Default del agregado cambiaría la seguridad del hilo principal; cambiar todo a Default sería incorrecto para E/S. |
| `StateFlow` | `BubbleGameViewModel.uiState: StateFlow<GameState>` y `records: StateFlow<GameRecordsState>`, observados por `BubbleGameScreen.collectAsStateWithLifecycle`. | UI ve estado nuevo sin consultar manualmente cada campo; la observación respeta el lifecycle de la pantalla. | Sin publicación observable, el usuario podría no ver aciertos, guardado, historial o estadísticas actualizados. StateFlow es parte del **repositorio existente**, no API enseñada de forma completa en el PDF. |
| `Flow` + `collectLatest` | `GameSessionDao.observeForOwner` emite listas Room; `loadHistory` usa `collectLatest` y `GameSyncScheduler.running` expone otro Flow. | Una modificación local o un GET que inserte filas dispara nuevo historial. `collectLatest` cancela el **bloque suspendido anterior** si aparece otra emisión; evita publicar un resultado antiguo tras el nuevo. | Con `collect` simple se podrían procesar todas las emisiones en fila y mostrar una estadística atrasada durante más tiempo. La función CPU pura no suspende en cada instrucción: cancelar no implica interrupción instantánea del cálculo interno. |
| `CancellationException` | Se vuelve a lanzar explícitamente en `BubbleGameViewModel` (carga, GET, encolado, espera), `GameSyncWorker` y `GameSyncProcessor` (POST). | Una cancelación por navegación/lifecycle/WorkManager debe conservar su semántica y no disfrazarse de error de red o «éxito». | Capturarla como `Exception` genérica podría reintentar un trabajo cancelado, mostrar un error falso o mantener trabajo innecesario. |
| `CoroutineWorker` | `GameSyncWorker.doWork()` se ejecuta cuando WorkManager satisface restricciones. | WorkManager administra ejecución diferida y reintentos aunque ya no esté abierta la pantalla Juegos. `doWork` traduce `Done`/`Retry` a `Result.success()`/`Result.retry()`. | Sustituirlo por una corrutina de Activity perdería el trabajo cuando se cierre esa pantalla y la planificación por conectividad/backoff. No equivale a un servicio permanente ni a ejecución inmediata. |

**Concurrencia efectiva:** se pueden solapar la observación Room, un GET remoto de la pantalla, un worker POST y la actualización local que produce el worker. La función de estadísticas recorre una lista en Default tras cada emisión; no hace múltiples cálculos simultáneos de una misma emisión ni paraleliza 20 burbujas. `collectLatest` ayuda a priorizar el historial reciente, condicionado a que sus partes sean cancelables.

**Otros límites del lifecycle:** `BubbleGameScreen` pausa en `ON_STOP`; el efecto que actualiza el tiempo usa `repeatOnLifecycle(STARTED)` y no necesita un hilo propio. `GameSyncWorker` no depende del ViewModel. `TokenStorage` se lee cuando se ejecuta el trabajo, no se almacena el token en el request WorkManager.

## 2. Cuatro cosas distintas que suelen confundirse

| Idea | En qué momento ocurre | Dónde está el dato y qué significa |
|---|---|---|
| **Persistir una partida** | Al completar 20: `completedSession` → `GameSessionRepository.save` → `GameSessionDao.insert`. | Una fila en Room con UUID y `syncStatus = pending`; puede existir sin internet ni sesión en backend. P2 la guarda **antes** de programar HTTP. |
| **Estar pendiente de sincronización** | La fila autenticada sigue en Room `pending` mientras falta confirmación remota. | `pendingForOwner(ownerId)` solo toma filas autenticadas del dueño. Invitados también conservan estado local `pending`, pero **nunca** se envían automáticamente. |
| **Recuperar historial remoto** | Al abrir Juegos con cuenta: `refreshFromBackend` → `GameHistoryRefresher.refresh` → GET. | Puede importar sesiones de otro dispositivo o confirmar una local equivalente; no crea una sesión nueva mediante POST ni sustituye el historial por la respuesta. |
| **Mostrar caché local mientras llega red** | `observeForOwner` emite Room y el ViewModel muestra filas/estadísticas; GET y worker pueden continuar aparte. | Room es persistencia en disco y fuente observable para UI. No hay un `LruCache` propio de Juegos. Un fallo de GET conserva lo ya almacenado. La primera emisión de Room y el GET se lanzan concurrentemente: no se garantiza cuál termina primero. |

### ¿Cómo se evitan duplicados?

1. **Una finalización = un UUID:** `BubbleGameViewModel.tap` detecta la transición a Finished y llama una sola vez a `completedSession`. `retrySave` reutiliza `pendingSession`.
2. **Local:** `GameSessionEntity.id` es clave primaria; `insert(IGNORE)` y `byId` impiden aceptar una colisión distinta como si se hubiera guardado correctamente.
3. **Envío:** `GameSessionRequest.id` es el mismo UUID en todos los intentos. `GameSyncProcessor` solo marca `synced` si `ack.id` coincide; el backend (`juegos.service.ts`) también es idempotente por UUID para el mismo usuario.
4. **GET:** `GameHistoryRefresher` busca `byId` antes de insertar y confirma únicamente si owner, fecha y métricas coinciden; no sobreescribe una colisión distinta. `GameStatistics` aplica además `distinctBy(id)` al historial filtrado.

### Escenarios de actualización

- **Primera ejecución sin caché:** lista vacía y estado de estadísticas vacío; si autenticado y GET falla, no se inventan partidas.
- **Fallo/offline:** guardado Room funciona; el worker espera conectividad o reintenta con backoff; la UI usa Room y explica que no pudo refrescar servidor.
- **Expiración y recuperación:** 401 → `blocked_auth`, 403 → `blocked_consent`, otros 4xx permanentes → `blocked_invalid`; después de reautenticarse, `restoreAfterLogin` devuelve solo `blocked_auth` de la cuenta actual a `pending`. No hay expiración temporal implementada para filas Room ni una política de TTL: un «dato desactualizado» solo se corrige con el GET al abrir Juegos si el servidor responde.
- **Conexión restaurada:** `AppContainer` puede encolar pendientes y WorkManager decide cuándo ejecutar. Verificar red del dispositivo no es prueba de que el backend conteste; por eso hay tratamiento separado de respuestas y errores.

## 3. Cómo explicar una media/precisión sin falsear los datos

Ejemplo didáctico, **no datos reales de un usuario**: dos partidas, cada una con 20 aciertos, una con 1 error y otra con 3. Precisión global = `(20 + 20) / (20 + 20 + 1 + 3) = 40/44 ≈ 90,9 %`. Si las duraciones fueron 3000 ms y 5000 ms, el promedio interno es `4000 ms` y el mejor es `3000 ms`; la UI los presenta como segundos. El historial se filtra por propietario antes de agregar, y la pantalla puede mostrar solo cinco filas aunque el promedio use todas.
